# Evolution Module

## 模块定位与边界

`se.evolution` 负责围绕问题台账推进持续改进闭环。它把质量检查、架构维护、测试补强和人工决策串成可恢复的循环。

本模块不替代 architecture、testing 或 quality 的内部规则。它只读取它们的稳定产物，并根据问题状态调度下一步动作。

## 对外提供能力

- 维护 `.se/project/evolution/registry/PROBLEM_REGISTRY.md`。
- 维护演进项目配置 `.se/project/evolution/project.config.yaml`。
- 生成人工决策项。
- 调度开发、验证、归档和停止报告。
- 通过脚本检查问题台账预算和循环状态。

## 对外依赖

- 读取 architecture 产物判断设计基线。
- 读取 testing 入口和测试结果判断验证状态。
- 读取 quality 报告发现结构问题。
- 读取 operator 决策文件处理需要人工判断的事项。

## 核心实体

- Problem Registry：唯一跨轮问题状态源。
- Problem Item：一个可推进、可验证、可归档的问题。
- Decision：需要人工裁决的结构化选项。
- Run Status：单轮改进运行状态。
- Evidence：修复和验证过程的证据。
- Archive：已解决或停止问题的归档记录。

## 功能清单

- 扫描问题台账并选择下一步问题。
- 计划修复或验证动作。
- 调度开发 Agent 和验证 Agent。
- 生成 operator 决策请求。
- 归档已解决问题。
- 在达到预算、阻塞或完成条件时停止。

## 业务规则

- `.se/project/evolution/registry/PROBLEM_REGISTRY.md` 是唯一跨轮问题状态源。
- 问题必须有明确状态、证据、下一步或阻塞原因。
- 需要人工判断时输出决策项，不把不确定性伪装成事实。
- 解决问题后必须有验证证据或明确的停止原因。
- 长日志和中间产物不写入台账正文，应通过证据路径引用。

## 权限规则

演进 Agent 可以更新 `.se/project/evolution/` 下的台账、状态、证据和归档。它调度修复时仍必须遵守仓库 worktree 规则和对应能力模块的写入边界。

## 状态或流程规则

演进循环流程：

1. 读取问题台账。
2. 判断是否存在等待人工决策的问题。
3. 选择可推进问题。
4. 调度开发或验证动作。
5. 写入状态和证据。
6. 输出 `continue`、`decide` 或 `stop`。

## 数据一致性要求

- 台账状态必须和 evidence、archive、decision 文件一致。
- 已归档问题不应继续作为 active 问题推进。
- 人工决策结果应能追溯到对应问题。
- 每轮状态文件只保留恢复所需事实，不保存完整历史流水。

## 用户交互流程

用户启动演进时，演进 Agent 从台账恢复状态，报告将推进的问题和原因。遇到多个合理路径时，输出精简决策项，包含背景、选项、影响、建议和生效范围。

## 不实现范围

- 不定义架构规范。
- 不编写测试执行细节。
- 不执行质量规则判定本身。
- 不把临时运行日志写入稳定项目态。
