# 质量规则与分级

本文档定义质量检查如何判定问题。它是运行时指南，主 Agent 和子 Agent 在解释结果、补充发现或分级时读取。

## 检查范围

质量系统只检查可以被仓库证据支持的可维护性信号：

- 模块依赖方向
- 单一职责和文件规模压力
- 测试代码隔离
- 领域词汇一致性
- 构建、测试和质量检查入口是否明确

它不替代安全审查、性能测试、产品验收或架构决策。

## 问题等级

| 等级 | 含义 | 默认处理 |
|---|---|---|
| `must_fix` | 违反硬性质量契约，或阻断可重复执行。 | 合并前修复，或登记明确例外。 |
| `should_fix` | 可维护性风险或提前预警。 | 规划清理，默认不阻断。 |

## 规则索引

| 规则 | 原则 | 默认等级 | 说明 |
|---|---|---|---|
| `QR001` | 依赖方向稳定 | `must_fix` | 模块导入必须符合项目依赖矩阵。 |
| `QR002` | 单一职责和可理解性 | `must_fix` / `should_fix` | 超过硬性文件规模阈值必须修复；超过预警阈值作为维护风险提示。 |
| `QR003` | 测试代码隔离 | `must_fix` | 生产代码不得混入测试支撑概念，也不得依赖测试便利实现。 |
| `QR004` | 领域词汇一致 | `must_fix` | 禁用或容易混淆的词汇不得漂移到源码中。 |
| `QR005` | 入口和约定清晰 | `must_fix` | 构建、测试和质量检查命令必须可重复、可说明。 |

## 事实性问题

事实性问题必须至少满足一个条件：

- 检查脚本输出了对应 finding。
- 源码、配置或文档中存在明确证据。
- 项目级上下文能被具体文件或命令结果支撑。

如果问题需要设计判断，必须标记为“评审判断”，并说明不确定性。
