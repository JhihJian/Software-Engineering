# registry-spec.md
# 问题台账契约

`PROBLEM_REGISTRY.md` 是当前任务看板。它必须让新的无上下文 agent 在 1-2 分钟内恢复当前状态，并避免承载全量历史。

---

## 长度边界

- 主台账保留当前状态、待处理问题、失败/阻塞问题、最近验证摘要和归档索引。
- 大段日志、全量测试输出、长失败分析、已解决历史必须移动到 `archive/` 或 `evidence/`。
- 单条问题备注超过 120 字时，改为摘要 + 证据链接。
- 硬性预算由 `se.evolution/framework/tools/check-registry-budget.sh` 检查：
  - 总行数 `<= 200`
  - 总字节数 `<= 35000`
  - `本轮已解决问题`、`最近验证摘要`、`归档索引`、`最近变更` 每节 `<= 40` 行
  - `本轮已解决问题` 表格 `<= 10` 行
  - `最近验证摘要` 表格 `<= 8` 行
  - `归档索引` 表格 `<= 10` 行
  - `最近变更` 表格 `<= 8` 行
- STEP 6.1 必须运行 `bash se.evolution/framework/tools/check-registry-budget.sh`。失败时不得继续追加主台账，必须先压缩到通过检查。

---

## 问题状态

| 状态 | 含义 | 下一步 |
|------|------|--------|
| `⏳ 待处理` | 已登记，尚未进入本轮开发 | 可进入计划 |
| `🛠 开发中` | 已分配给开发子代理 | 等待开发门控 |
| `🔍 验证中` | 开发门控通过，等待验证 | 调度验证 |
| `❌ 验证失败` | 验证未通过或证据不足 | 转下轮重试 |
| `⏸ 等待确认` | 架构/需求/文档冲突 | 暂停等用户 |
| `✅ 已解决` | 验证通过，尚未归档 | 进入交付归档 |
| `📦 已归档` | 已提交到 git | 仅保留索引 |

允许流转：

```
⏳ 待处理 -> 🛠 开发中 -> 🔍 验证中 -> ✅ 已解决 -> 📦 已归档
🔍 验证中 -> ❌ 验证失败 -> ⏳ 待处理
任意状态 -> ⏸ 等待确认
```

---

## 主台账最小结构

`PROBLEM_REGISTRY.md` 至少包含：

1. `全局状态`：当前轮次、阻塞条件、下一轮入口、下一个新问题 ID。
2. `待处理问题`：ID、标签、优先级、状态、依据、下一步。
3. `验证失败/等待确认`：失败轮次、原因摘要、证据路径、重试或确认条件。
4. `最近验证摘要`：验证命令、通过/失败数量、证据路径。
5. `归档索引`：轮次、问题 ID、commit hash、证据路径。

---

## 幂等性规则

- 同一问题在同一轮只能被一个开发组领取。
- 已归档问题不得重新打开；若发现回归，创建新问题 ID 并引用原问题。
- 验证失败不得覆盖旧证据，只能追加新轮证据链接。
- 未通过验证的问题不得标记为 `✅ 已解决`。
- 未成功提交到 git 的问题不得标记为 `📦 已归档`。

---

## 归档规则

`se.evolution/framework/prompts/loop.md` STEP 6 按本节执行 `✅ 已解决` → `📦 已归档` 的状态迁移。

**Commit 范围：**

- 把本轮通过验证的业务代码、测试、`PROBLEM_REGISTRY.md` 更新作为一个或多个 commit 提交
- 不得把用户/外部已有改动混入本轮 commit
- commit 完成后在 `归档索引` 节记录 commit hash

**Commit message 规范：**

必须以问题 ID 收尾，便于追溯。示例：

```
fix: close SEC-007 stale token validation
test: cover SEC-008 upload authorization
chore: update improvement registry
```

**失败或未通过时：**

- 不得提交为完成态
- 在 `PROBLEM_REGISTRY.md` 记录失败 diff 范围和证据
- 将问题状态置为 `❌ 验证失败` 或保留 `⏳ 待处理`
- STEP 5.1 裁决依据动作裁决表："已验证改动本轮未能归档"（首次出现 → `continue`；同一 `blocker_kind=archive_failure` 与核心原因连续出现 → `continue` + `result=needs_guidance`，由外层写运行指引后继续）

**归档后清洁度：**

- 工作区应只剩用户明确保留的未提交改动
- 若仍有未归档改动，必须在本轮 summary 列出原因和文件清单
